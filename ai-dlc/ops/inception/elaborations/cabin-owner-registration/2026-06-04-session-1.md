## Discussion Notes

### Key Decisions

| Decision | Reasoning |
|---|---|
| Use Supabase Auth email/password — no custom auth | Per ADR-001 and project rules |
| Frontend handles auth state reactively via `onAuthStateChange` | Per code-standards.md — avoids redirect loops |
| Cabin entity uses free-text address for location | Simplest MVP; geocoding is out of scope |
| Amenities stored as string array in PostgreSQL | Simple, queryable, no join table needed for MVP |
| .NET API validates JWT via JWKS endpoint | Per ADR-005 — ES256 asymmetric validation |
| RLS on cabins table restricts to owner | Per EC-007 — server also validates ownership |

### Deferred / Out of Scope

| Item | Why Deferred |
|---|---|
| Email verification | Not needed for MVP login flow |
| Password reset | Can be added later via Supabase built-in |
| Cabin image uploads | Adds complexity (storage, CDN) — later intent |
| Multi-community isolation | NF-03 deferred until multiple resorts onboard |
| Edit/delete cabin | Separate intent — this is create + view only |

## Units Identified

### Unit 1 — User Registration
**Purpose:** A new user can create an account with email and password.
**ACs:**
1. Given a valid email and password (≥8 chars), when the user submits registration, then an account is created and they are redirected to login
2. Given an email already in use, when submitted, then a clear error is shown without revealing whether the email exists
3. Given an invalid email format, when submitted, then client-side validation prevents submission

**Edge cases:** Rate limiting on registration endpoint (defer to Supabase built-in)

### Unit 2 — User Login
**Purpose:** A registered user can authenticate and receive a session.
**ACs:**
1. Given valid credentials, when the user submits login, then they are authenticated and redirected to the dashboard
2. Given invalid credentials, when submitted, then a generic error is shown (not "wrong password" specifically)
3. Given a logged-in user visiting /login, then they are redirected to the dashboard

**Edge cases:** EC-008 — JWT expiry handled by onAuthStateChange

### Unit 3 — Protected Route Shell
**Purpose:** Authenticated routes are inaccessible without a valid session.
**ACs:**
1. Given an unauthenticated user, when they navigate to a protected route, then they are redirected to /login
2. Given an authenticated user, when they navigate to a protected route, then the page renders with a layout (nav + content area)
3. Given a user whose session expires, when they next interact, then they are redirected to /login

### Unit 4 — Create Cabin Profile
**Purpose:** A logged-in cabin owner can create a cabin with basic details.
**ACs:**
1. Given a logged-in user, when they submit a valid cabin form (name, location, capacity, amenities), then the cabin is persisted and visible on their dashboard
2. Given missing required fields (name, location, capacity), when submitted, then validation errors are shown per field
3. Given capacity < 1, when submitted, then validation rejects with "Capacity must be at least 1"
4. Given a valid request, when the API creates the cabin, then the cabin's owner_id matches the authenticated user (server-enforced)

**Edge cases:** EC-007 — RLS ensures cabins.owner_id = auth.uid()

### Unit 5 — View Cabin Dashboard
**Purpose:** A logged-in user sees a list of their cabins on the dashboard.
**ACs:**
1. Given a user with one or more cabins, when they visit the dashboard, then all their cabins are listed with name, location, and capacity
2. Given a user with zero cabins, when they visit the dashboard, then an empty state is shown with a prompt to create their first cabin
3. Given multiple users, when user A views the dashboard, then only user A's cabins are shown (never user B's)

**Edge cases:** EC-007 — RLS filters at database level; server also validates
