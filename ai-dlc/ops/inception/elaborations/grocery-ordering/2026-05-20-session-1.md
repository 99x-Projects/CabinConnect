## Discussion Notes

### Key Decisions

| Decision | Reasoning |
|---|---|
| Use "Host" not "cabin owner" | Aligns with domain glossary; "cabin owner" is not a recognised domain term |
| No in-platform payment for groceries | Reduces scope and avoids Stripe integration complexity in phase 1 |
| Volunteer is a new auth role | Guests and Hosts cannot fulfill deliveries; a distinct role is needed |
| Admin populates the catalog | Prevents scope creep into supplier management |
| Delivery address sourced from Cabin record | Cabin entity already stores location; no new address model needed |
| One volunteer per order | Simplifies assignment logic; split fulfilment deferred |
| Grocery orders are standalone (not Booking-linked) | Hosts may need to stock cabins outside of guest stays |

### Deferred / Out of Scope

| Item | Why Deferred |
|---|---|
| In-platform grocery payment | Payment integration adds significant scope; cash/offline acceptable for phase 1 |
| Volunteer vetting | Trust/safety concern outside platform's current risk surface |
| GPS delivery tracking | Requires real-time infrastructure not currently in place |
| Guest-initiated orders | Needs new Guest-facing surface; Host-only covers primary use case first |
| Scheduled delivery windows | Adds scheduling complexity; deferred to phase 2 |
| Order tied to a Booking | Linkage can be added as an optional field in phase 2 |

## Prompts Used

### Prompt 1 — Feature Decomposition

```
We are building CabinConnect — a cabin booking platform with a .NET 8 Web API backend,
React + TypeScript frontend, and Supabase (PostgreSQL) as the database.

Feature: Grocery Ordering for Hosts
Description: Hosts can browse a grocery catalog, place orders, and choose between
self-pickup or volunteer doorstep delivery to their cabin.

Break this feature down into the smallest independent Units of work that can be built,
tested, and deployed separately. For each Unit, output:
- Unit name
- One-sentence purpose
- Key acceptance criteria (Given/When/Then format)
- Dependencies on other Units
```

**Output summary:** Decomposed into 6 units covering catalog browse, order placement,
volunteer registration, assignment, fulfillment, and status tracking.

### Prompt 2 — Edge Case Discovery

```
Context: CabinConnect — cabin booking platform. .NET 8 API, React/TypeScript, Supabase.
Feature: Grocery Ordering for Hosts with volunteer delivery.

What edge cases should we handle for this feature? Consider:
- Volunteer lifecycle (registration, assignment, dropout)
- Order lifecycle (placement, cancellation, fulfillment failure)
- Data integrity (cabin address missing, items out of stock)
- Concurrency (two volunteers accepting same order)
```

**Output summary:** Identified EC-011 through EC-015 (see Edge Cases section below).
