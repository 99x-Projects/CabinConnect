## Discussion Notes

### Key Decisions

| Decision | Reasoning |
|---|---|
| Amenities are a predefined enumerable set | Free-text amenities create inconsistency in search and display; enum enforces a clean data model from the start |
| Location is a plain text field for MVP | No map/geocoding integration required; reduces scope significantly |
| Capacity = max guests only | Bedroom/bed counts deferred; max guests is the booking-critical field |
| Inactive cabins remain visible to the owning Host | Hosts need to manage and potentially reactivate cabins; hiding them would create confusion |
| Deactivate/Reactivate is idempotent | Prevents errors when UI re-submits on network retry; cleaner UX |
| `403` for wrong-owner cabin access | Makes ownership enforcement explicitly testable; note to team: may prefer `404` to avoid leaking ID existence |

### Deferred / Out of Scope

| Item | Why Deferred |
|---|---|
| Cabin pricing (Base Rate / Seasonal Rate) | Separate intent — pricing logic is complex enough to own its own elaboration |
| Photo / image uploads | Infrastructure complexity; not required for MVP profile functionality |
| Visitor instructions (MC-05, MC-06) | Separate intent — different access model (guests without full accounts) |
| Maintenance tracking (MC-03) | Separate intent |
| Cost estimation (MC-04) | Separate intent |
