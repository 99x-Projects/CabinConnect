## Discussion Notes

### Key Decisions

| Decision | Reasoning |
|---|---|
| Five units extracted | Each behaviour is independently testable and deployable; stays under the 8-unit ceiling |
| Amenity Catalog as first unit | Register and Update depend on a stable predefined list; custom amenities are additional free-text values |
| Capacity bounds: min 1, max 50 | Aligns with domain (at least 1 guest); 50 is a practical ceiling for cabin accommodation |
| Deactivation does not cancel Bookings | Guest experience protected; deactivated Cabin is hidden from Guest discovery and new booking attempts; existing Confirmed/Pending Bookings remain valid |
| No hard delete | Matches intent assumption; deactivation is the only removal path |
| Schema/RLS in Register Cabin scope | First write path establishes the Cabin entity; no separate infra-only unit |

### Deferred / Out of Scope

| Item | Why Deferred |
|---|---|
| Guest-facing cabin browse/search | Explicitly out of scope in intent |
| Photo uploads | Out of scope in intent |
| Pricing and availability | Separate intents |
| React UI for profile management | Units define API behaviour; frontend bolt can follow |
| Geocoding / map display for street address | Intent limits location to street address text only |
