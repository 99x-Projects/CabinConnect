## Discussion Notes

The session followed the strict one-unit-at-a-time interactive protocol: propose name+purpose → confirm → propose ACs → confirm → propose edge cases & open questions → confirm → next unit. After five units the engineer signed off the full summary table.

### Key Decisions
| Decision | Reasoning |
|---|---|
| Communities are admin-seeded via a repo seed file; no admin CRUD UI in MVP | Engineer stated "first resort are add by admin"; minimal infra, version-controlled, auditable |
| Generic `users` table with `role` enum (default `owner`) | Requirements.md introduces multiple roles (admin/resident/volunteer); avoids a future rename migration |
| Lazy provisioning of `users` row on first authenticated API call | Simpler than Supabase Auth webhook; idempotent via PK `ON CONFLICT DO NOTHING` |
| Email verification disabled for MVP | Smoother sign-up; revisit before public launch |
| One cabin per owner in MVP (`UNIQUE(owner_id)`) | Engineer constraint: "one owner can have one cabin in mvp"; simplifies endpoints to `/me` |
| `/me` endpoints throughout (not `/cabins/{id}`) | Makes the one-cabin-per-owner rule explicit in the URL; prevents ID-tampering attack surface |
| `PUT` (full replace) + last-write-wins | Small field set, low concurrency from a single owner; revisit if races appear |
| Sensitive operational data in a separate table & endpoint | Guarantees public DTO can never leak it; gives future security-hardening unit one place to encrypt |
| Free-text address (MVP) | Faster; revisit when Groceries delivery requires structured address |
| Amenities validated against a seeded enum table | No redeploy needed to add amenities; admins can extend later |
| Explicit JWT issuer/audience/JWKS validation in .NET | Don't rely on default middleware behaviour; write it down once |

### Deferred / Out of Scope
| Item | Why Deferred |
|---|---|
| Admin CRUD UI for communities | Seed file in repo sufficient for MVP |
| Password reset, email verification, social/OAuth login | Each is its own unit/intent |
| Account deletion / GDPR erasure | Separate compliance-focused unit |
| Cabin deletion / soft-delete | Separate unit |
| Cabin photos | Intent open question; defer |
| Multi-cabin per owner; cabin transfer | Future intent after MVP |
| Visitor / guest sharing of operational data | MC-05/MC-06 — separate intent |
| Column-level encryption of operational data | Security-hardening unit |
| Field-level audit history | Audit unit |
| Optimistic concurrency / etag | Revisit if last-write-wins causes issues |
| Pagination, HTTP caching on community list | Premature for MVP volumes |

### Cross-Cutting Concerns Surfaced (Not Acted On)
- **CLAUDE.md vs Requirements.md mismatch.** CLAUDE.md §1/§4 describes a booking platform (Guest/Host/Booking/Hold) but Requirements.md describes a four-module community app (MyCabin, Events, Groceries, ToolShare). Requirements.md was treated as source of truth. Candidate for a future improvement to reconcile the glossary and CLAUDE.md.
