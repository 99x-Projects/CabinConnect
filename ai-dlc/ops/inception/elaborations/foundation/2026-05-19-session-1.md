## Discussion Notes

### Key Decisions

| # | Decision | Reasoning |
|---|---|---|
| D-1 | `community_id` is a `NOT NULL` FK on every Community-scoped table, *not* a nullable column. | Nullable scoping leaks data on faulty joins. Forced-NOT-NULL makes "I forgot to scope" a compile-time / migration-time error, not a runtime bug. |
| D-2 | The user's *active* Community is encoded as a custom JWT claim issued at sign-in (or context switch), not derived per-request from a DB lookup. | Latency + correctness — every API call needs the active Community; doing a per-request DB lookup is too costly and races against context switches. |
| D-3 | Multi-Community users have a "switch active Community" action that triggers re-issuing the JWT with the new active claim. | Cleanest model: one active Community per session-token; switching is an explicit user action with a clear audit trail. |
| D-4 | RLS policies are *generated by a template* invoked from each migration, not hand-written per table. | Hand-written RLS policies have historically been a top source of bugs. Templating removes the room for human error and means every new table inherits the policy correctly by construction. |
| D-5 | The cross-Community isolation test harness lives at the *API integration* layer, not the unit-test layer. | Unit tests on the RLS policies are insufficient — we need to assert the *combined* behaviour (middleware + RLS + handler). The harness runs an "alien user from Community Y" against every endpoint and asserts 404 with no leak. |
| D-6 | Locale is stored on the `users` row as a column, **not** in a separate preferences table. | The user record is loaded on every authenticated request anyway; making locale a separate lookup is a needless join. Also affects D-2 — JWT claim can include locale. |
| D-7 | The cache layer (CI-13) keys on `(user_id, route)`, not `(community_id, route)` or `(device_id, route)`. | Per-user isolation is correct: if user A signs out and user B signs in on the same device, B must not see A's cached data. User-key purges cleanly on sign-out. |
| D-8 | "Critical reads" are *explicitly tagged at the API layer* (a response header `X-Cabin-Cache-Profile: critical-24h`), not guessed by the frontend. | Keeps the offline policy a server-owned decision so we can change it without a frontend redeploy. Tag values are: `critical-24h`, `standard`, `no-cache`. |
| D-9 | Foundation Bolt intentionally exceeds the 3–8 Units guideline (final count: 10 Units). | The cluster spans 4 Intents; the Foundation Bolt is a one-off shape (per the cluster convention in CLAUDE.md §5.1). Subsequent Bolts will return to 3–8. |

## Prompts Used

### Prompt 1 — Cluster Decomposition (used once for all 4 Intents combined)

```
Context: CabinConnect is a 4-module digital community platform for Norwegian
mountain resort communities. Tech stack: .NET 8 Web API backend, React 18 +
TypeScript + Vite frontend (PWA), PostgreSQL via Supabase with RLS, Supabase
Auth. Each Community (resort) is fully data-isolated.

We are running a Foundation Cluster Mob Elaboration covering four
tightly-coupled foundational Intents:
  - CI-01: Community Boundary & Data Isolation
  - CI-02: Cabin Owner Registration & Authentication
  - CI-13: Offline-First Caching for Critical Reads
  - CI-14: Norwegian + English Localization

[Full What/Why/Success/Assumptions for each Intent pasted from the four
Intent files; full §10 NFRs and §11 Risks from PRD pasted.]

Propose the smallest set of independently testable Units that together
fulfil all four Intents. For each Unit, output:
  - Unit ID (U-NNN) and name
  - One-sentence purpose
  - Owning Intent (which CI it primarily belongs to)
  - Cross-Intent design decisions baked in (cite by D-N if a Key Decision)
  - Dependencies on other Units in this cluster
  - Top-3 edge cases this Unit must handle

Do NOT include implementation details. Focus on behaviour.
Constraint: target 8–12 Units total (Foundation Bolt is slightly larger
than a normal Bolt by design).
```

**Output summary:** Claude proposed 11 candidate Units. Asitha and Claude consolidated two (the RLS policy generator and cross-community isolation test harness were initially separate; the harness was folded into U-003 as an AC since the middleware is what gets tested). Final: 10 Units.

### Prompt 2 — Acceptance Criteria (used once per Unit, 10 invocations)

```
Context: CabinConnect Foundation Cluster, Unit <U-NNN — name>.
Domain glossary, Key Decisions D-1 through D-9, and relevant NFRs are loaded.

Unit purpose: <one sentence>
Owning Intent: <CI-NN>

Write acceptance criteria for this Unit in strict Given/When/Then format:
- Each criterion independently testable
- One behaviour per criterion (no compound ACs)
- Cover the happy path AND the top 3 edge cases identified in Prompt 1
- Include at least one criterion that asserts the cross-Intent decision
  baked into this Unit (e.g. JWT claim shape, RLS policy presence, cache
  key structure)

Also output the In Scope / Out of Scope lists for this Unit.
```

**Output summary:** ACs ranged from 4 to 8 per Unit depending on Unit complexity. Each Unit's edge-case coverage was cross-checked against EC-001..EC-007 from CLAUDE.md §9. Three new edge cases were surfaced during this prompt (see Edge Cases Discovered below).

## Edge Cases Discovered

New edge cases surfaced during this session — to be added to `ai-dlc/guidelines/edge-cases.md` and reflected in the corresponding Unit ACs.

| ID | Description | Origin |
|---|---|---|
| EC-008 | A user belonging to multiple Communities switches active Community mid-session; an in-flight request issued under the old JWT must not write data into the new Community. | D-3 + Prompt 2 AC review on U-003 |
| EC-009 | A user signs out on a shared device that has cached critical reads; the next user signing in must see only their own Community's data — never the previous user's cached state. | D-7 + U-008 AC review |
| EC-010 | A push notification is queued for a user whose locale was changed between queue time and delivery time; the notification must be rendered in the user's *current* locale, not the locale at queue time. | U-010 AC review |

> All three are added to `ai-dlc/guidelines/edge-cases.md` as `EC-008`, `EC-009`, `EC-010` immediately after this session, per the "edge cases captured DURING elaboration" rule (CLAUDE.md §5.1).
