## Context

Wire `react-i18next` on the frontend with two locale bundles (`nb-NO`, `en`). Wire a parallel message bundle on the .NET backend for system messages (emails, push notifications, API error messages). Establish the key naming convention. Catch parity drift between locales at CI time.

## Acceptance Criteria

- Given the React app is built, when it loads, then `react-i18next` is initialized with both `nb-NO` and `en` bundles loaded.
- Given a developer references a translation key that does not exist in the active locale's bundle, when the app runs in development, then a console warning identifies the missing key.
- Given a developer references a translation key that does not exist in the active locale's bundle, when the app runs in production, then the key falls back to the default (Bokmål) bundle silently (no console noise).
- Given the .NET API is built, when it loads, then the backend message bundles for `nb-NO` and `en` are loaded.
- Given an API error or system message is generated by the backend, when sent to the client, then the message body is rendered in the locale of the requester (resolved per U-010).
- Given a developer introduces a new translation key, when the build runs, then a CI parity check fails if the key exists in `nb-NO` but is missing in `en` (or vice versa).
- Given the user's locale is `nb-NO`, when the frontend bootstraps, then `react-i18next`'s active locale is `nb-NO`.

## Scope

**In scope:**
- `react-i18next` initialization
- Backend message bundle wiring (.NET resource files or JSON equivalent)
- Key naming convention (kebab-case, scope.subscope.key — e.g. `cabin.list.empty-state`)
- Missing-key warnings in dev
- Locale-parity CI check

**Out of scope:**
- Translation content (filled in per feature, not in this Unit)
- The locale resolution chain itself (U-010)
- Date / number / currency formatting beyond what bundle strings include (deferred — lean on browser `Intl` for MVP)
